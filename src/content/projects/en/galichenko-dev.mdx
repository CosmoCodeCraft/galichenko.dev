## Context and requirements

The project started from a simple requirement — create a personal website that could be shared with employers, faculty and colleagues.

Before implementation, I defined the readers and the depth of information each would need:

- a hiring manager scanning projects quickly;
- a technical lead evaluating engineering depth;
- a faculty member looking for research publications;
- a colleague following a direct link to a specific project or publication.

That requirement analysis shaped both the page hierarchy and the content model instead of leaving them as consequences of implementation.

## Information architecture and content model

Home provides a quick first impression; Projects, Research and Notes provide browsable archives; and detail pages carry the engineering or scholarly depth. Project pages record the problem, contribution, decisions and evidence, while publication pages expose abstracts, bibliographic metadata, identifiers and available resources.

Projects, publications and notes are stored as structured content. Typed Content Collection schemas define the metadata for each type, so new records can normally be added without changing page components. The routing and content structure also anticipate future localization, although English remains the only enabled public language.

## Static technical architecture

The site uses Astro and TypeScript to generate static pages. That architecture fits a public archive whose content changes through the repository and does not need a runtime backend, database or client-side application shell.

Content and presentation remain separate, but the source of truth stays in typed files rather than a CMS. This avoids authentication, hosting and operational infrastructure that the current project does not require.

## Research and publication tooling

Publication records carry richer scholarly metadata than project or note entries: titles, authors, status, source and conference details, abstracts, keywords, eLIBRARY and EDN identifiers, related projects, and links to local or external full text where available. The same record powers the archive, detail route, sitemap and citation interface.

The “Cite this work” tool deterministically generates GOST R 7.0.5–2008, IEEE, APA 7 and BibTeX citations from that stored metadata. It does not depend on runtime requests to external scholarly services. Local PDFs, publisher pages, external full text and scholarly records remain distinct resource types rather than interchangeable links.

## Validation, deployment and implementation workflow

GitHub Actions validates and builds the site before deploying the static output to GitHub Pages. The deployed site uses the custom `sergeygalichenko.dev` domain, while content, application code and deployment configuration remain version-controlled together.

Codex is used extensively as an implementation tool. I define the requirements, architecture, content model and acceptance criteria, then review changes and decide what enters the site; AI assistance does not replace human technical ownership.

## Current scope and evidence

The site intentionally avoids a runtime backend, database, user accounts, CMS and complex analytics infrastructure because none currently solves a project requirement. Localization is architecturally anticipated but not enabled.

The live site and public repository provide the evidence: typed Content Collections, publication schemas and routes, deterministic citation tooling, publication resources, project case studies, and the automated GitHub Pages workflow.
